# Mascoma Lake — layered SVG export for Figma

Generated by `build_svg.py`. **A port, not a redraw** — every shape comes from the artifacts the app
ships, and the paint is the app's own style evaluated at the matching zoom.

```bash
python3 exports/mascoma/build_svg.py                  # both presets, ~2 min
python3 exports/mascoma/build_svg.py --lake-width 640 # one-off size
```

## Sizing: you specify the lake, not the canvas

The lake's bbox is only **33.9%** of the frame's width — the other two thirds are the 3 mi buffer. So
sizes here are *how wide the lake itself should be*, which is the dimension you actually design to.

| preset | lake | canvas | zoom |
| --- | --- | --- | --- |
| `mobile` | 400 px | 1181 × 1177 | z13.16 |
| `desktop` | 1000 px | 2953 × 2943 | z14.49 |

Scale depends only on zoom, so the buffer changes the canvas size and *nothing else*. Want a 400px
lake on a tighter canvas? Drop `BUFFER_MILES`; the zoom and every stroke width stay identical.

Six files, `mascoma-{composite,basemap,lake}-{mobile,desktop}.svg`. Within a preset all three share
one `viewBox`, so they stack perfectly in one frame.

## Why target size drives zoom (and why a flat 1px stroke would break it)

Vector-tile roads are **lines whose weight is the stroke**, not geometry — only water and landuse are
real shapes. So flattening every stroke to 1px destroys the highway > major > minor hierarchy.

Instead, each preset asks the question the app already answers: *what does this look like at the zoom
where the lake is N pixels wide?* Protomaps' width expressions are functions of zoom, so evaluating
them there thins each road **proportionally to its class**:

| | highway | major | minor | other |
| --- | --- | --- | --- | --- |
| mobile (z13.2) | 2.40 | 1.93 | 0.75 | 0.50 |
| desktop (z14.5) | 4.04 | 2.60 | 1.53 | 0.69 |

The mobile file is not the desktop one shrunk. It's the app at z13.2 — different stroke weights,
fewer labels, coarser generalisation, read from z13 tiles instead of z14.

## Layer tree

`Basemap` holds **one group per Protomaps style layer, in the style's own draw order** — `earth`,
`landuse_park`, `water`, `roads_minor_casing`, `roads_minor`, … That order is what puts casings under
their roads, so keep it if you reorder anything.

Within a group, shapes are merged into one `<path>` per distinct (colour, width, dash) bucket —
select one object, change one fill, every minor road moves together. Labels are individual `<text>`.

`Bathymetry` is one group per depth (`10 ft` … `70 ft`), each holding one path per isobath ring
(`Depth-10ft-01` …), so a single line is selectable without ungrouping.

| | value | source |
| --- | --- | --- |
| basemap | Protomaps `dark` flavor | `layers('protomaps', namedFlavor('dark'))` |
| earth / water / forest | `#1f1f1f` / `#31353f` / `#192a24` | ” |
| lake fill / shoreline | `#3a6ea5` / `#9ecae1` | `WATER_PALETTE.dark` |
| contours | `#155671` → `#63e0f9`, 0.75 opacity | `CONTOUR_PALETTE.dark`, `CONTOUR_OPACITY` |

The contour ramp **inverts** between themes — in dark mode *deep* water is the bright cyan. It's
scaled to this lake's deepest drawn ring (70 ft) per `contourColorExpression`, not to the corpus.

Shoreline is 2.5px: `water-outline` is 1 at rest and 2.5 when selected, and contours only render with
the drawer open (D81), so 2.5 is the state that pairs with them.

## Two things that bite when you scale

**SVG geometry is exact — it does not degrade.** But two things do:

1. **Figma's resize is not a scale.** Dragging a frame's handles (or typing W/H) moves geometry and
   leaves stroke weight and font size untouched, so a 3× shrink makes strokes read 3× heavier and
   labels collide. The Scale tool (`K`) scales all three together. Using the right preset avoids the
   question entirely.
2. **Contour crowding is cartographic, not numerical.** Isobaths on a steep drop-off are genuinely a
   few metres apart, so below some output size they are sub-pixel and merge however precise the path
   is. The fix is to draw fewer, not to add accuracy: `--contour-step 2` keeps only every 20 ft, and
   rings shorter than `MIN_RING_PX` (6px at output size) are dropped as slivers.

## Known deviations from the live map

1. **Label placement is approximate.** Point labels are exact; line labels sit at the midpoint of the
   longest segment at a fixed rotation, where MapLibre curves text along the spline. Collision *is*
   modelled — greedy box rejection, prioritised by importance (towns > lakes > major > minor roads),
   which is deliberately not MapLibre's placement order since that lets a lane name beat a town.
2. **Labels under the lake.** App layers draw above the basemap, so the water fill covers basemap
   labels — the Shaker village names really are clipped in the app. Anything more than half covered
   is dropped; the rest are kept. **To show them, drag the label groups above `Mascoma Lake`.**
3. **`text-field` is simplified** to `name:en` → `name` → `pgf:name`. The real expression is a
   multi-script `format` tree; the shortcut is correct for this region.
4. **Casings are flattened.** MapLibre's `line-gap-width` draws two strokes either side of the
   centreline; here it's one stroke of `gap + 2 × width` beneath the road — the same picture.
5. **Sprites are dropped** — no route shields, POI icons or townspots; those are PNG atlases.
6. **Geometry is simplified** to `SIMPLIFY_PX` (0.25px at output size), which is invisible at 100%
   and roughly halves file size.

## The ice frame — 22 December 2025

`build_imagery.py` writes `mascoma-ice-20251222-{mobile,desktop}.png`: transparent canvases on the
**same frame and the same pixel dimensions** as the SVGs, so they drop straight underneath.

Source is the N6e freeze-up archive (`VITE_IMAGERY_ARCHIVE_URL`), season `winter-2025-26`, granule
**`S2B_18TYP_20251222_0_L2A`** — Sentinel-2B, 2025-12-22T15:50:59Z, 2.9% granule cloud.

**Not NAIP.** The aerial tier is 0.3 m and far sharper, but NAIP is flown mid-summer on a 2–3 year
cycle for the USDA's crop program, so it can never show ice. Any dated winter frame is Sentinel.

**The feather is already in the pixels** — the cutter bakes alpha server-side (`featherMeters: 240`,
`erosionMeters: 20`, its `feather_proximity` stage). That is `SENTINEL_MASK_METERS` 60/240, *not* the
aerial tier's 20/80: at a 10 m ground sample a 20 m buffer is two pixels, so the aerial numbers would
render as a hard edge. `build_imagery.py` therefore computes no feather of its own.

Resolution: z14 is the archive's max, giving **2108 px** across this frame (~9.55 m/px in 3857, at
Sentinel's native 10 m). So `mobile` (1181 px) is fed from *above* native and is genuinely sharp;
`desktop` (2953 px) upsamples ~1.4× and is correspondingly soft. There is no sharper winter frame.

Two details worth knowing:

- **RGB is premultiplied before resampling and unpremultiplied after.** The archive's transparent
  pixels do not necessarily hold black, so resampling colour independently of alpha drags whatever
  they carry into the fade as a dark fringe.
- **Only Mascoma is revealed.** The granule masks all 1,167 bodies it covers, so the raw frame lights
  up Crystal Lake, Smith Pond and the rest. The default narrows to Mascoma with a soft-edged
  selection 360 m out — clear of the 240 m feather, softened because the outlet channel runs
  continuously off the north-west tip and a hard cut there reads as a tear. `--all-bodies` keeps
  everything, which is what the app's viewport-wide reveal actually shows.

### What the frame says about the ice

The cutter's own zonal statistics for Mascoma that day:

| | |
| --- | --- |
| coverage / clear | 100% / 99.1% |
| SCL **water** | 96.2% |
| SCL **snow-ice** | 1.3% |
| mean NDSI | −0.31 |

⚠ **The classifier calls it water, and that is consistent with black ice rather than evidence against
it.** Clear ice over dark water is spectrally almost indistinguishable from open water, and NDSI at
−0.31 is firmly in the not-snow range (snow runs above ~+0.4). So an SCL-driven read would score this
day as "no ice" on a lake that was skateable — which is the gap `docs/reading-ice-from-orbit.md`
covers and why the archive also carries Sentinel-1 `vh` radar frames. Do not build an ice indicator
off `snowIcePct` alone.

**Required credit: `Copernicus Sentinel data 2025–2026`** (`copernicusCredit`). Unlike NAIP's — public
domain, courtesy only — this one is obligatory.

⚠ **Layer zoom gates are load-bearing.** 23 of the 71 style layers carry `minzoom`/`maxzoom`, and the

why the first version of this export looked heavy. `layer_visible()` is not optional.

## Reusing this for another lake

1. `pnpm exec convex run waterBodies:get '{"waterBodyId":"<id>"}' > src/<lake>-body.json`
2. `grep '"bodyId":"<externalId>"' contours.geojsonl > src/<lake>-contours.geojsonl`
3. Point `BODY` / `CONTOURS` at them.

For light mode, regenerate the style with `namedFlavor('white')` and swap the four app colours for
`WATER_PALETTE.white` / `CONTOUR_PALETTE.white`. Note the dark flavor has **71** style layers and the
white one **69** — the sets genuinely differ, so the style JSON must be regenerated, not recoloured.
